# Оптимизация прикреплений по времени пути

Первый этап минимизирует время пути от точки внутри ячейки до места приёма. Готовый сценарий использует единое прикрепление для машины и пешего пути. Если минимум пешего времени среди всех 38 больниц строго больше 60 минут, назначение выбирается по минимуму автомобильного времени. Иначе минимизируется арифметическое среднее автомобильного и пешего времени среди всех 38 больниц, без отдельного ограничения пешего времени кандидатов. Ровно 60 минут входит в ветвь среднего. Пробки, мощность и штраф за смену учреждения в целевую функцию пока не входят.

Правило согласовано пользователем для симуляции. Часовой порог относится к выбору целевой функции, а не объявляется универсальным нормативом из PDF. Слой нормативных превышений по просьбе пользователя не добавлен.

Сначала вычисляется одна больница для каждой ячейки. Затем оба файла времени получают этот же ID и одни и те же новые зоны, но разные времена пути. При равном значении критерия сохраняется исходное учреждение, затем используется стабильный порядок ID. По заполненным матрицам получено 12 620 ячеек в ветви машины и 7 223 в ветви среднего; изменено 4 729 прикреплений. Индивидуальное время одного транспорта может вырасти ради уменьшения среднего; это показано цветом изменений и в карточке ячейки. Файл `data/optimization/joint-allocation.json.gz` сохраняет единое назначение, использованную ветвь и значения критерия.

## Готовый сценарий для исходных 38 точек

В текущем готовом сценарии заполнены все 19 843 ячейки для обоих способов передвижения. Каждый отсутствующий элемент матрицы заменён арифметическим средним восьми ближайших заполненных ячеек для той же больницы и того же транспорта. Донорами служат только исходные найденные времена OSRM, уже заполненные ячейки не используются повторно. При сплошном пустом фрагменте выбираются ближайшие заполненные ячейки за его пределами. Затем назначения, времена «до/после», итоговые средние и полные векторные зоны вычислены заново по дополненной матрице.

Сырые ответы OSRM сохранены без изменений в `data/optimization/*-matrix.json.gz`; дополненные матрицы — в `*-completed-matrix.json.gz`. `prepared-meta.json` хранит метод заполнения, количество замен и прежние итоги только по найденным маршрутам. На карте и в подсказках отдельной маркировки заполненных ячеек нет. Поэтому текущие средние относятся ко всей дополненной сетке, а не только к подтверждённым дорожным маршрутам. Перезаполнение без обращений к OSRM: `node scripts/fill-optimization-neighbors.mjs`.

По запросу пользователя все исходные 38 точек разрешены для этого сценария. Полные матрицы выполнены заранее на локальных дорожных графах отдельно для машины и пешего пути, а назначения вычислены совместно по правилу выше. Пользовательская страница содержит только оптимизацию: прежние вкладки «Карта» и «Таблицы» и их фоновая загрузка удалены из входной страницы. Начальный вид — величина изменения времени на одной карте, без цветных границ поверх заливки. Переключение транспорта загружает соответствующие времена без изменения нового прикрепления. Матрица, поиск назначения и объединение зон в браузере не выполняются; OSRM для просмотра не нужен. Пересборка общего назначения без запросов OSRM: `node scripts/prepare-joint-allocation.mjs`.

Файлы `public/optimization/prepared-auto.json.gz` и `prepared-pedestrian.json.gz` содержат назначения, времена «до/после», разницу и объединённые зоны. `prepared-meta.json` связывает их контрольными суммами с неизменной сеткой и исходными точками. Просмотр не зависит от старых настроек и доступности IndexedDB. Можно переключать «До/После», накладывать время, менять прозрачность и включать исходные границы пунктиром.

Для общего масштаба заранее объединены соседние ячейки с одинаковой больницей и цветовым интервалом времени. Это сохраняет точную окраску исходных ячеек без усреднения. При масштабе 11 и выше карта показывает сами ячейки с их индивидуальными временами. Подробная сетка и численные итоги не меняются из-за масштаба отображения.

Время и контуры рисуются Canvas-поверхностями в движущемся пейне Яндекс Карт. Используются масштаб, локальное окно и преобразование координат самого пейна, включая анимацию. Контейнер движется вместе с подложкой; Canvas размещается в его локальном окне с запасом по краям. Это заменяет прежнюю привязку к неподвижному экрану, из-за которой слой смещался во время перетаскивания. Нативными объектами остаются только метки учреждений. Кэш проецированных Path2D общий между картами с одинаковой проекцией. Подробные ячейки выбираются пространственным индексом. Изменение прозрачности не пересобирает геометрию.

Доступны три режима: «Рядом» — две карты с синхронной камерой; «Ползунок» — две одинаковые области карты, правая обрезана разделителем; «Наложение» — одна карта с переключением исходного и нового состояния и исходными границами пунктиром поверх новых. Центр и масштаб сохраняются при смене режима. Разделитель доступен мышью, касанием и клавишами стрелок. Для времени используется общая шкала цветов; «Где стало быстрее» включает отдельный слой величины сокращения времени. Его цвет для неизменившегося времени — светлый бежевый, для увеличения — розовый. По нажатию на ячейку видны обе больницы, оба времени и изменение.

Окна карт изолированы через `overflow: hidden`, `isolation` и ограничение отрисовки контейнером: запас движущегося Canvas не может выходить на соседнюю карту. Цвета подложки приглушены. По умолчанию ячейки без смены больницы показаны светлым фоном, а цвет выделяет изменённые прикрепления; это можно отключить. В слое времени границы нейтральные и выключены по умолчанию. Цвета учреждений используются только в отдельном виде прикреплений; исходные границы при наложении показаны синим пунктиром. Насыщенность регулирует только один активный цветовой слой.

Контуры для отображения подготовлены отдельно в `result.boundaries` и не подменяют исходную геометрию расчёта. В метрической проекции фрагменты одного учреждения повторно объединяются, удаляются повторные и вырожденные вершины, закрываются щели и убираются иглы шириной менее нескольких метров. Порог обработки — 2 м, существенно меньше шага сетки. У линий округлые стыки; тонкие внутренние обрывки не обводятся как самостоятельные границы. Заливка прикреплений и ячейки используют исходную геометрию, поэтому очистка контуров не меняет владельца территории, покрытие, времена или показатели. Подготовка контуров без перерасчёта маршрутов: `node scripts/prepare-display-boundaries.mjs`. Ступенчатость реальных границ по сетке 250 м / 2 км сохраняется; более точное распределение требует более мелкой расчётной сетки.

Полные матрицы и отчёты с идентификаторами дорожных графов находятся в `data/optimization/`. В них представлены все 19 843 × 38 пар для каждого способа передвижения, включая недоступные. Для воспроизводимого предварительного расчёта: `node scripts/precompute-optimization.mjs --routing-root PATH_TO_PREPARED_LOCAL_ROUTING`. Повторный запуск использует завершённые порции в `.tmp/`; в имени набора сохранения учтены сетка, все точки, дорожные графы и расчётный модуль. Запросы идут только в локальный OSRM; радиус привязки к дорогам остаётся 1 км. При `NoSegment` исключается только указанная OSRM точка, остальные пары считаются. Увеличение радиуса и подстановка времени по прямой не применяются.

Готовые данные встроены в код: `scripts/embed-optimization-data.mjs` создаёт модули из подготовленных gzip-файлов, проверяя SHA-256. Сборка включает их в локальные JavaScript-ресурсы; пеший результат подгружается при выборе транспорта. Пользовательская страница не содержит собственного расчёта, импорта, выгрузки и раздела выбора больницы. Ручная загрузка данных и OSRM для просмотра не нужны.

Метки больниц открывают отдельные карточки учреждения, ячейки — сравнение «до/после». Карточки находятся вне контейнеров карт; поддерживают перенос длинных названий и прокрутку, закрываются кнопкой и Escape. Нажатие на метку не должно открывать карточку лежащей под ней ячейки.

## Входные данные

Новый перечень содержит один лист, 229 объектов 40 учреждений и четыре исходных поля: «Наименование учреждения», «Тип объекта 8000 форма», «Наименование объекта», «Сборный адрес». У одного объекта адрес отсутствует. Координат и сведений о фактическом приёме терапевта нет. Нормализованный перечень с номерами строк и SHA-256 источника находится в `public/optimization/facilities.json`.

Новые объекты не разрешены автоматически и не участвуют в готовом сценарии. Для их включения в следующую подготовку необходимо подтвердить координаты и фактический приём взрослых терапевтом. Текущий интерфейс показывает только согласованный сценарий исходных 38 точек. Детские, специализированные и стационарные корпуса не считаются терапевтическими автоматически.

## Сетка

В 19 городах используется шаг 250 м, вне них — 2 км. Маска городов взята из полигонов населённых пунктов OpenStreetMap, а не из границ городских округов с сельскими территориями. Список: Алексин, Белёв, Богородицк, Болохово, Венёв, Донской, Ефремов, Кимовск, Киреевск, Липки, Новомосковск, Плавск, Советск, Суворов, Тула, Узловая, Чекалин, Щёкино, Ясногорск. Посёлки городского типа в эту маску не включены.

Сначала исходные зоны обрезаются по городской маске и её дополнению. Затем строится сетка каждого шага. На границах получаются отдельные фрагменты: они сохраняют исходное прикрепление, не перекрываются и вместе покрывают ту же территорию. У каждого фрагмента есть точка маршрутизации внутри него. Получено 19 843 фрагмента: 11 402 городских и 8 441 вне городов. Это расчёт территории, не реестр проживающих людей; данных о числе взрослых жителей в каждой ячейке пока нет.

`public/optimization/grid.json.gz` содержит сетку и привязку к SHA-256 исходного снимка. `grid-meta.json` содержит контрольную сумму, алгоритм и количества. Перестроение после изменения границ: `node scripts/build-optimization-grid.mjs`. Городские полигоны и дата данных находятся в `cities.geojson`. Дорожные данные и границы: © OpenStreetMap contributors, ODbL.

## Расчёт

Используется локальный [OSRM Table Service](https://github.com/Project-OSRM/osrm-backend/blob/master/docs/http.md#table-service). Запросы ограничены loopback-адресами. Размер порции — до 32 отправлений и 32 назначений, привязка к дороге — до 1 км. Время асимметрично: считается именно от ячейки к месту приёма. `fallback_speed` не используется. `NoSegment` делится на меньшие порции, чтобы одна неподходящая точка не обнулила остальные. Недоступная пара остаётся `null`.

Для каждой ячейки сравниваются все 38 согласованных точек по совместному правилу машины и пешего пути, приведённому в начале документа. Новое назначение общее для двух видов транспорта. ML и обучение для такого независимого выбора не требуются. Исходные времена рассчитаны на той же смешанной сетке до прежней больницы; снимок 5 км не растягивается на мелкие ячейки.

Средние «до/после» относятся ко всей дополненной сетке, без весов населения. Ненайденные времена заполнены описанным выше методом соседей; исходные матрицы сохранены отдельно. Расчёт и объединение зон выполняются при подготовке файлов, а не при открытии пользовательской страницы.

## Слои

Сравнение доступно рядом, ползунком и наложением. Пользователь выбирает время пути, зоны прикрепления или изменение времени; исходные границы можно включить пунктиром. Переключатель транспорта меняет значения времени при общем новом прикреплении. Технические пояснения и происхождение данных в интерфейсе не выводятся.

## Применение приложенных методических рекомендаций

В «Территориальном планировании региональных систем здравоохранения», 2023, разделы 5.2.1–5.3 (печатные страницы 18–21), предлагаются фактическое и целевое состояния сети, сравнение по профилям помощи и тепловые карты времени доезда. Это отражено двумя сценариями и наложением времени. Здание без подтверждённого профиля помощи не считается взаимозаменяемым объектом.

Упомянутые в разделе 5.2.1.3 двадцать минут относятся к скорой помощи. Они не перенесены в модель посещения терапевта. Таблица 3 на печатных страницах 34–35 содержит дополнительные критерии для малых поселений, включая расстояние, общественный транспорт, дороги и кадры; эти критерии пока не вычисляются. Цветовые интервалы 15/30/60 минут — шкала визуализации, не заключение о нормативном соответствии.

Для следующего этапа понадобятся согласованные ограничения мощности по точкам приёма, спрос в одной единице времени, взрослое население по ячейкам, штат/расписание терапевтов и правила допустимых переводов. Плановое число посещений учреждения за смену нельзя напрямую сравнивать с числом прикреплённых жителей.

## Ручная приёмка

1. Распаковать готовый архив, запустить `START.cmd`. Оптимизация должна открыться с готовым результатом без импорта, OSRM и ранее сохранённых данных браузера.
2. Переключить машину и пеший путь. Новая больница для одной ячейки должна совпадать; времена меняются. Все ячейки заполнены.
3. Проверить режимы «Рядом», «Ползунок», «Наложение», синхронность камер и отсутствие смещения слоя при перетаскивании. Включить исходные границы и изменить насыщенность.
4. Нажать на метку больницы: должны отображаться её название, прикрепление, площади зон и пропускная способность. Карточка ячейки не должна заменять её.
5. Нажать на ячейку: видны обе больницы, оба времени и изменение. Проверить длинное название, небольшую высоту окна, прокрутку и закрытие кнопкой и Escape.
6. Проверить отсутствие удалённых технических пояснений, разделов «Как выбрана больница» и «Свой расчёт и выгрузка». Перезагрузка должна снова показывать готовые данные.
7. Открыть `developer.html` напрямую; доступ и прежние инструменты разработчика сохранены.
